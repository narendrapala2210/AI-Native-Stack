# 03. `try`, `except`, `else` & `finally` Clauses

## 📖 Concept Overview
Python's complete exception handling statement includes four complementary clauses:

```python
try:
    # 1. Code that may raise an exception
except SomeException:
    # 2. Runs ONLY if SomeException was raised
else:
    # 3. Runs ONLY if NO exceptions were raised in the try block
finally:
    # 4. ALWAYS runs, regardless of whether exceptions occurred or not!
```

---

### 1. The `else` Clause
The code inside `else` runs **only if the `try` block executed to completion with zero exceptions**.
- **Best Practice**: Place only the dangerous code in `try`, and put code that relies on the success of `try` in `else`. This prevents accidentally catching unexpected errors from secondary statements!

---

### 2. The `finally` Clause (Clean-Up Guarantee)
The `finally` block **always executes**, even if:
- An exception was raised and caught.
- An unhandled exception was raised and crashed the program.
- A `return`, `break`, or `continue` statement was executed inside `try` or `except`!
> **Primary Use**: Releasing resources (closing file descriptors, releasing database locks, terminating network sockets).

---

## 🛠️ Practical Hands-On & Real-World Examples

### Example 1: Database Resource Clean-Up Guarantee with `finally`
Demonstrate that `finally` runs to close a connection even when an unhandled exception or return occurs.

```python
class MockDatabaseConnection:
    def open(self):
        print("-> [DB] Connection opened.")
    def query(self, sql: str):
        print(f"-> [DB] Executing query: '{sql}'")
        if "FAIL" in sql:
            raise RuntimeError("Database query failed due to lock contention!")
    def close(self):
        print("-> [DB] Connection safely CLOSED and returned to pool.")

def execute_user_report(sql_command: str):
    db = MockDatabaseConnection()
    db.open()
    try:
        db.query(sql_command)
    except RuntimeError as err:
        print(f"-> [HANDLER] Caught database error: {err}")
    else:
        print("-> [SUCCESS] Query executed smoothly with zero errors.")
    finally:
        # Guarantees connection closure in all scenarios!
        db.close()
    print("Function completed.\n")

execute_user_report("SELECT * FROM users;")
execute_user_report("SELECT * FROM FAIL_TABLE;")
```

**Step-by-Step Explanation**:
1. On successful query, `try` -> `else` -> `finally` execute.
2. On error query, `try` -> `except` -> `finally` execute.
3. In both cases, `db.close()` runs without fail.

**Expected Console Output**:
```text
-> [DB] Connection opened.
-> [DB] Executing query: 'SELECT * FROM users;'
-> [SUCCESS] Query executed smoothly with zero errors.
-> [DB] Connection safely CLOSED and returned to pool.
Function completed.

-> [DB] Connection opened.
-> [DB] Executing query: 'SELECT * FROM FAIL_TABLE;'
-> [HANDLER] Caught database error: Database query failed due to lock contention!
-> [DB] Connection safely CLOSED and returned to pool.
Function completed.
```

### Example 2: The Return Value Override in `finally` (Gotcha)
Expose the subtle gotcha where returning from inside a `finally` block overwrites return values from `try` or `except`.

```python
def test_finally_return_behavior():
    try:
        return "VALUE_FROM_TRY"
    finally:
        # WARNING: Returning from finally overrides all previous returns!
        return "OVERRIDDEN_BY_FINALLY"

result = test_finally_return_behavior()
print(f"Function returned: {result}")
```

**Step-by-Step Explanation**:
1. Python prepares to return `"VALUE_FROM_TRY"`.
2. Before returning, it executes `finally`. Because `finally` contains its own `return`, it overwrites the prepared value.
3. Best practice: never place `return` inside `finally`.

**Expected Console Output**:
```text
Function returned: OVERRIDDEN_BY_FINALLY
```

### Example 3: Atomic State Restoration via `finally`
Ensure an application's global maintenance flag is always reset back to normal operations after a batch job completes.

```python
class MaintenanceManager:
    is_maintenance_mode = False

    @classmethod
    def run_critical_job(cls, should_fail: bool):
        cls.is_maintenance_mode = True
        print(f"[STATUS] Maintenance mode enabled: {cls.is_maintenance_mode}")
        try:
            print("Running database schema migration...")
            if should_fail:
                raise ValueError("Migration script encountered invalid column syntax!")
            print("Migration completed successfully.")
        finally:
            # Always reset maintenance mode
            cls.is_maintenance_mode = False
            print(f"[STATUS] Maintenance mode disabled: {cls.is_maintenance_mode}\n")

# Run successful job
MaintenanceManager.run_critical_job(should_fail=False)

# Run failing job
try:
    MaintenanceManager.run_critical_job(should_fail=True)
except ValueError as e:
    print(f"Trapped Top-Level Error: {e}")
```

**Step-by-Step Explanation**:
1. Even though an unhandled `ValueError` propagates out of `run_critical_job`, `finally` executes first.
2. Guarantees the system does not get stuck in maintenance mode.

**Expected Console Output**:
```text
[STATUS] Maintenance mode enabled: True
Running database schema migration...
Migration completed successfully.
[STATUS] Maintenance mode disabled: False

[STATUS] Maintenance mode enabled: True
Running database schema migration...
[STATUS] Maintenance mode disabled: False

Trapped Top-Level Error: Migration script encountered invalid column syntax!
```
