## 1. Conceptual Deep-Dive: The Anatomy of Injection Vulnerabilities

Injection flaws (OWASP Top 10 #3) occur when untrusted user input is concatenated directly into command strings, query templates, or shell scripts without parameterization:
1. **SQL Injection (SQLi)**: An attacker injects SQL syntax into query strings, allowing them to bypass authentication, read sensitive tables, or drop databases.
2. **OS Command Injection**: Unsanitized user inputs passed to system shells (`os.system` or `subprocess.run(shell=True)`) enable attackers to execute arbitrary operating system commands.

```
VULNERABLE (Concatenation):
"SELECT * FROM users WHERE name = '" + user_input + "'"
Input: "' OR '1'='1" -> Query evaluates to TRUE for all rows!

SECURE (Parameterized Query):
cursor.execute("SELECT * FROM users WHERE name = ?", (user_input,))
Input: "' OR '1'='1" -> Treated strictly as a literal string value!
```

---

## 2. Vulnerability Comparison & Defenses

| Injection Type | Vulnerable Pattern | Secure Defense |
|---|---|---|
| SQL Injection | `f"SELECT * FROM users WHERE id = {user_id}"` | `cursor.execute("SELECT * FROM users WHERE id = ?", (user_id,))` |
| Command Injection | `subprocess.run(f"ping {host}", shell=True)` | `subprocess.run(["ping", "-c", "1", host], shell=False)` |
| Dynamic Code Execution | `eval(user_expression)` | `ast.literal_eval(expression)` or structured grammar parser |

## 3. Practical Code Examples with Step-by-Step Explanations

### Example 1: Parameterized SQL Queries vs. String Concatenation
Demonstrate SQL injection vulnerability and how parameterized queries prevent it.

```python
import sqlite3

# Set up in-memory database
conn = sqlite3.connect(":memory:")
cursor = conn.cursor()
cursor.execute("CREATE TABLE users (id INTEGER PRIMARY KEY, username TEXT, is_admin INT)")
cursor.execute("INSERT INTO users (username, is_admin) VALUES ('alice', 1), ('bob', 0)")
conn.commit()

# Attacker input designed to bypass authentication
malicious_input = "' OR '1'='1"

# VULNERABLE APPROACH (Do not use!):
vulnerable_query = f"SELECT * FROM users WHERE username = '{malicious_input}'"
print("Vulnerable SQL Query:")
print(f"  {vulnerable_query}")
cursor.execute(vulnerable_query)
print(f"  Vulnerable Result (Leaks all accounts): {cursor.fetchall()}\n")

# SECURE APPROACH (Parameterized queries):
secure_query = "SELECT * FROM users WHERE username = ?"
cursor.execute(secure_query, (malicious_input,))
print("Secure Parameterized Query:")
print(f"  Query: {secure_query} with parameter ({malicious_input!r})")
print(f"  Secure Result (Safe, 0 accounts leaked): {cursor.fetchall()}")

conn.close()
```

#### Step-by-Step Explanation:
1. Concatenating user input modifies the SQL syntax structure, evaluating `'1'='1'` to true for all rows.
2. Parameterized queries send query structure and parameters to the database engine separately.
3. The database engine treats the parameter strictly as literal text, preventing syntax manipulation.

#### Expected Output:
```text
Vulnerable SQL Query:
  SELECT * FROM users WHERE username = '' OR '1'='1'
  Vulnerable Result (Leaks all accounts): [(1, 'alice', 1), (2, 'bob', 0)]

Secure Parameterized Query:
  Query: SELECT * FROM users WHERE username = ? with parameter ("' OR '1'='1")
  Secure Result (Safe, 0 accounts leaked): []
```

### Example 2: Preventing OS Command Injection in `subprocess`
Execute system tools safely without invoking the system shell.

```python
import subprocess
import shlex

def ping_host_vulnerable(host: str):
    # DANGEROUS: shell=True with unquoted string
    cmd = f"echo Ping target: {host}"
    return subprocess.check_output(cmd, shell=True, text=True)

def ping_host_secure(host: str):
    # SECURE: Argument list with shell=False
    # Command and arguments are passed as discrete elements
    cmd = ["echo", f"Ping target: {host}"]
    return subprocess.check_output(cmd, shell=False, text=True)

# Attacker attempts command chaining using semicolon
attacker_payload = "localhost; whoami"

print("Secure Execution with Argument List:")
safe_output = ping_host_secure(attacker_payload)
print(f"  Output: {safe_output.strip()}")
print("  Notice: Semicolon was passed as a literal string argument, not a command delimiter!")
```

#### Step-by-Step Explanation:
1. `shell=True` passes input strings to `/bin/sh` or `cmd.exe`, which interpret special characters (`;`, `&`, `|`).
2. Passing arguments as an explicit list (`["echo", host]`) invokes the executable directly via `execve`, disabling shell metacharacter parsing.

#### Expected Output:
```text
Secure Execution with Argument List:
  Output: Ping target: localhost; whoami
  Notice: Semicolon was passed as a literal string argument, not a command delimiter!
```

### Example 3: Safe Expression Parsing with `ast.literal_eval`
Evaluate user-supplied data strings without using dangerous `eval()`.

```python
import ast

def safe_parse_user_input(payload_str: str):
    try:
        # ast.literal_eval parses only basic Python literals (strings, numbers, tuples, lists, dicts, booleans)
        return ast.literal_eval(payload_str)
    except (ValueError, SyntaxError) as e:
        print(f"Rejected dangerous or invalid input: {e}")
        return None

# Safe payloads evaluate correctly
data = safe_parse_user_input("{'settings': {'dark_mode': True}, 'version': 2}")
print(f"Parsed configuration: {data}")

# Malicious payload attempting arbitrary code execution
malicious_payload = "__import__('os').system('echo HACKED')"
result = safe_parse_user_input(malicious_payload)
print(f"Evaluation of dangerous code: {result}")
```

#### Step-by-Step Explanation:
1. `eval()` executes arbitrary Python code, allowing attackers to access `os`, delete files, or read environment variables.
2. `ast.literal_eval()` accepts only primitive Python literals, rejecting function calls, imports, and expressions.

#### Expected Output:
```text
Parsed configuration: {'settings': {'dark_mode': True}, 'version': 2}
Rejected dangerous or invalid input: malformed node or string on line 1: <ast.Call object at ...>
Evaluation of dangerous code: None
```

---

## 4. Key Takeaways & Best Practices

1. Never use string interpolation (f-strings, `%`, `format()`) to build SQL queries.
2. Avoid `subprocess.run(..., shell=True)` whenever possible; pass arguments as an explicit list.
3. Replace `eval()` with `ast.literal_eval()` or dedicated schema validators like Pydantic.
