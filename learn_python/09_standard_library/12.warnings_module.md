## 1. Conceptual Deep-Dive: Warnings vs. Exceptions

In Python, software anomalies fall into two distinct operational paradigms:
1. **Exceptions (`raise Exception`)**:
   - Fatal conditions that disrupt program execution unless explicitly caught with `try/except`.
   - Used for invalid inputs, missing resources, network failures, or syntax violations.
2. **Warnings (`warnings.warn`)**:
   - Non-fatal notifications that inform developers or operators of sub-optimal practices, upcoming breaking changes, or deprecated APIs **without terminating program execution**.
   - Configurable at runtime, in test suites, or via command-line flags (`python -W error`).

```
Runtime Anomaly
      |
      +---> Fatal? (Cannot proceed) ---------------> Raise Exception (Halts execution)
      |
      +---> Non-Fatal? (Informational / Deprecation) -> warnings.warn()
                                                           |
                                 +-------------------------+-------------------------+
                                 |                         |                         |
                           Default Display            Filtered / Ignored      Promoted to Error
                          (Prints to stderr)         (warnings.filterwarnings)  (-W error)
```

## 2. Built-in Warning Categories Hierarchy

| Warning Class | Typical Trigger Scenario |
|---|---|
| `UserWarning` | Default category; generic notifications emitted by user code |
| `DeprecationWarning` | Warns developers that a feature will be removed in future releases |
| `FutureWarning` | Warns end users of semantic changes to an existing feature |
| `RuntimeWarning` | Warns of suspicious runtime behavior (e.g. numerical overflow in float math) |
| `SyntaxWarning` | Warns of suspicious syntax (e.g. using `is` with literals) |
| `ResourceWarning` | Warns of unclosed files, sockets, or subprocesses (enabled with `-X dev`) |

## 3. Practical Code Examples with Step-by-Step Explanations

### Example 1: Emitting Targeted Deprecation Warnings
Signal to library consumers that an older API endpoint will be phased out.

```python
import warnings

def legacy_fetch_user_data(user_id: int):
    # Emit DeprecationWarning with stacklevel=2 so warning points to caller line
    warnings.warn(
        "legacy_fetch_user_data() is deprecated and will be removed in v2.0. Use UserClient.get_profile() instead.",
        category=DeprecationWarning,
        stacklevel=2
    )
    return {"id": user_id, "name": "Legacy User Profile"}

def client_application():
    # Calling deprecated API
    user = legacy_fetch_user_data(42)
    print(f"Retrieved User: {user['name']}")

client_application()
```

#### Step-by-Step Explanation:
1. `warnings.warn()` issues a non-fatal message to `sys.stderr`.
2. `category=DeprecationWarning` classifies the notification so tooling can filter it accordingly.
3. `stacklevel=2` ensures the warning message attributes the violation to line 16 (`client_application()`) rather than line 5 inside the library function.

#### Expected Output:
```text
...: DeprecationWarning: legacy_fetch_user_data() is deprecated and will be removed in v2.0. Use UserClient.get_profile() instead.
  user = legacy_fetch_user_data(42)
Retrieved User: Legacy User Profile
```

### Example 2: Filtering Warnings and Converting Warnings into Errors
Enforce zero-warning code quality in CI/CD test pipelines.

```python
import warnings

def risky_calculation(val: int):
    if val < 0:
        warnings.warn(f"Negative value {val} detected; result may be non-deterministic.", category=RuntimeWarning)
    return val * 2

# Scenario A: Filter and ignore warnings
warnings.filterwarnings("ignore", category=RuntimeWarning)
result_ignored = risky_calculation(-5)
print(f"Scenario A (Ignored): Result = {result_ignored}")

# Scenario B: Promote warnings to fatal exceptions
warnings.filterwarnings("error", category=RuntimeWarning)
try:
    risky_calculation(-10)
except RuntimeWarning as err:
    print(f"Scenario B (Promoted to Error): Successfully caught '{err}' as fatal exception!")

# Reset warning filters back to default
warnings.resetwarnings()
```

#### Step-by-Step Explanation:
1. `warnings.filterwarnings("ignore", ...)` suppresses matching warnings entirely.
2. `warnings.filterwarnings("error", ...)` causes the warning to be raised as a full exception, forcing developers to resolve deprecated code before merging.
3. `warnings.resetwarnings()` restores the default system filter rules.

#### Expected Output:
```text
Scenario A (Ignored): Result = -10
Scenario B (Promoted to Error): Successfully caught 'Negative value -10 detected; result may be non-deterministic.' as fatal exception!
```

### Example 3: Capturing Warnings in Unit Test Suites with `catch_warnings`
Assert that code emits required deprecation or configuration warnings during automated testing.

```python
import warnings

def legacy_config_parser(raw_text: str):
    if "=" not in raw_text:
        warnings.warn("Malformed configuration row, missing '=' separator", category=UserWarning)
        return {}
    k, v = raw_text.split("=", 1)
    return {k.strip(): v.strip()}

def test_warning_emission():
    # Context manager isolates warning interception from global state
    with warnings.catch_warnings(record=True) as captured_warnings:
        # Cause all warnings to be recorded
        warnings.simplefilter("always")

        # Trigger warning
        result = legacy_config_parser("INVALID_ROW_FORMAT")

        # Assertions on captured warnings
        assert len(captured_warnings) == 1, "Expected exactly 1 warning"
        recorded = captured_warnings[0]
        assert issubclass(recorded.category, UserWarning)
        assert "missing '='" in str(recorded.message)
        print(f"Test Passed: Captured {recorded.category.__name__}: '{recorded.message}'")

test_warning_emission()
```

#### Step-by-Step Explanation:
1. `with warnings.catch_warnings(record=True) as captured_warnings:` records all warnings emitted inside the block into a list without printing to stderr.
2. `captured_warnings[0]` exposes attributes like `category`, `message`, `filename`, and `lineno`.
3. This pattern enables automated test assertions verifying API deprecation notices.

#### Expected Output:
```text
Test Passed: Captured UserWarning: 'Malformed configuration row, missing '=' separator'
```

## 4. Key Takeaways & Best Practices

1. Use `warnings.warn()` instead of `print()` when alerting consumers about deprecated or non-standard practices.
2. Always specify `stacklevel=2` (or higher) so the warning points to the user's calling code, not the library's internal utility.
3. In CI/CD pipelines, execute tests with `python -W error` to prevent new code from introducing deprecated API dependencies.
